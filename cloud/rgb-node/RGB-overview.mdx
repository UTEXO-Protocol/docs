RGB Node exposes RGB asset issuance, invoicing, and transfers through a REST API. It targets teams that need on-chain RGB support without embedding the full RGB protocol stack in their own backend. It covers the same asset layer as the [RGB Lightning Node](/cloud/rgb-lightning-node-api), but settles directly on Bitcoin L1 rather than over Lightning channels — a practical starting point when Lightning isn’t a near-term requirement, with a clear upgrade path once volume justifies it.

<Info>
  Source repository: [`UTEXO-Protocol/rgb-node-api`](https://github.com/UTEXO-Protocol/rgb-node-api) (first-party Rust implementation). A third-party Rust implementation is also available at [`RGB-OS/rgb-node-rust`](https://github.com/RGB-OS/rgb-node-rust).
</Info>

## Who should use RGB Node

- **Exchanges** can integrate RGB Node directly into their backend. It is designed to sit behind your own infrastructure and expose asset issuance, balances, and transfers to internal systems.
- **Wallets** should integrate through the [Utexo SDK](/product-suite/sdk) rather than running RGB Node directly. The SDK wraps the same functionality for client-side use and is the supported path for wallet integrations.

<Warning>
  RGB Node is infrastructure software, not a hosted or shared service. Running a node grants visibility into wallet activity, xpubs, and UTXO metadata — even though private keys are never held by the node itself.

  Deploy RGB Node only within infrastructure you directly control: an exchange backend, internal settlement system, or enterprise custody environment. Confirm the operating team understands and accepts this privacy exposure before deployment. RGB Node is not appropriate for environments where this trust boundary cannot be maintained.
</Warning>

## What RGB Node provides

| Capability | Description |
| :-- | :-- |
| Asset issuance | Issue RGB20 (NIA) assets directly on Bitcoin L1 |
| Invoicing | Create blinded invoices to receive RGB assets |
| Transfers | Build unsigned PSBTs, accept signed PSBTs, finalize and broadcast |
| Multi-wallet | Manage multiple RGB wallets concurrently, each scoped by its own xpubs |
| UTXO management | List unspents, create UTXOs, rotate receive addresses |
| Transfer history | List transactions and RGB transfers per asset |
| Refresh worker | Background sync that tracks transfers until they settle or fail |

## Architecture: watch-only, external signing

RGB Node operates on watch-only wallets. It holds no private keys and never signs transactions.

- Wallets are registered using extended public keys (xpubs).
- Transfer endpoints follow a **begin/end pattern**: the `*begin` endpoint returns an unsigned PSBT; the client signs it locally; the `*end` endpoint accepts the signed PSBT for finalization and broadcast.
- All `/wallet/` calls are scoped per wallet using three request headers: `xpub-van`, `xpub-col`, and `master-fingerprint`.

The custody boundary stays on the client side. RGB Node can run as a semi-trusted API within your infrastructure without becoming a key-management liability. For production deployments, pair it with a dedicated signer — see [`RGB-OS/thunderlink-signer`](https://github.com/RGB-OS/thunderlink-signer) for a reference implementation.

## Underlying library

RGB Node is built on `rgb-lib`, the Rust library that handles RGB state management and PSBT construction. Both RGB Node and the Utexo SDK wrap `rgb-lib` internally. Most integrators will not interact with it directly. See the [Glossary](/getting-started/glossary) for definitions of key terms.
