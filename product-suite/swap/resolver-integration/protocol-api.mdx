Resolvers call the Protocol API on Utexo. Utexo calls the resolver through the [Resolver API callbacks](/product-suite/swap/resolver-integration/resolver-api).

The interactive reference for these endpoints is the [Resolver API Swagger](https://stage.swagger.swap.utexo.com/docs/).

## Authentication

Every request must include your resolver API key:

```http
X-API-Key: <your_api_key>
```

Requests with missing or invalid keys are rejected.

## Error envelope

Protocol errors use this envelope:

```json
{
	"code": 1,
	"message": "Internal server error",
	"entity": "Intent",
	"details": null
}
```

## Discovery

### `GET /v1/networks`

Lists supported networks. The optional `token` query parameter filters networks by token. Response items include:

| Field | Description |
| --- | --- |
| `id` | Numeric network identifier. |
| `name` | Human-readable network name. |
| `type` | Network family. |
| `supports_optimized_swap` | Whether the network supports optimized single-chain swaps. |
| `icon_url` | Icon asset URL. |
| `supports_custom_tokens` | If `true`, the token list is not exhaustive and custom tokens may be swapped. |

### `GET /v1/tokens`

Lists supported tokens. Query parameters:

| Parameter | Type | Description |
| --- | --- | --- |
| `limit` | integer | Page size. |
| `offset` | integer | Page offset. |
| `q` | string | Symbol or contract address filter. |
| `network_id` | integer | Restrict to a network. |

Response:

```json
{
	"data": [
		{
			"network_id": 1,
			"name": "<token name>",
			"contract_address": "<token address>",
			"symbol": "<symbol>",
			"icon_url": "<URL>",
			"wrapped_token_address": null
		}
	],
	"pagination": {
		"limit": 20,
		"offset": 0,
		"pages": 1,
		"total": 1
	}
}
```

### `GET /v1/resolvers/webhooks/public-key`

Returns the Ed25519 public key used to verify webhook signatures.

```json
{ "public_key": "<hex-encoded Ed25519 public key>" }
```

## Intents and swaps

### `GET /v1/intents/{id}`

Retrieves an intent. Statuses:

| Status | Meaning |
| --- | --- |
| `Initiated` | Intent created and awaiting user approval. |
| `ApprovalAdded` | User approval received. |
| `Accepted` | Intent accepted by the resolver and being executed. |
| `Declined` | Intent declined. |
| `Lapsed` | Intent deadline passed before the required action. |
| `AwaitingBroadcast` | The user must fund the intent and report the source transaction. |

The response includes `from_chain`, `to_chain`, `from_token`, `to_token`, user addresses, amounts, `quote_id`, `resolver_id`, `affiliate_id`, `flow_kind`, `swap_type`, `deposit_type`, `nonce`, `deadline`, and lifecycle timestamps. `deadline` is an RFC 3339 timestamp. `secret_hash` is not included in this response.

### `GET /v1/intents/status/pending`

Lists `ApprovalAdded` intents assigned to the authenticated resolver. Query parameters are `limit`, with default `20`, and `offset`, with default `0`. The response uses `data` and `pagination`.

### `POST /v1/intents/{id}/accept`

Accepts an intent. The response carries the data the resolver needs for the `deposit` transaction: `system_contract_address`, `permit2_contract_address`, `permit2_signature`, `proxy_address`, `fulfillment_signature`, `psbt`, and `cosign_transaction`. Which fields are meaningful depends on the source chain.

Accept applies to the permit flow. Other funding flows return HTTP `409` with error code `64`. Ownership mismatches return HTTP `403` with code `65`.

### `POST /v1/intents/{id}/decline`

Declines an intent. The body is optional:

```json
{ "error_code": 1, "message": "quote expired" }
```

Decline applies to the permit flow. Success returns HTTP `200` with an empty body.

### `POST /v1/intents/{intent_id}/refund`

Refunds the user's locked funds without waiting for the timelock to expire.

### `GET /v1/resolvers/stream`

Opens a WebSocket stream for the resolver (HTTP `101 Switching Protocols`). Send the `X-API-Key` header on the upgrade request.

### `GET /v1/intents/{intent_id}/swap`

Retrieves the on-chain execution record for an intent. The response includes `status`, `proxy_address`, transaction hashes for deposit, fulfillment, withdrawal, swap, and refund, intermediate-token data, and lifecycle timestamps.

## Reporting transactions

The reporting endpoints record source deposits, destination fulfillments, source withdrawals, and atomic swaps.

### `POST /v1/intents/{id}/deposit`

```json
{ "tx_hash": "<transaction hash>" }
```

### `POST /v1/intents/{id}/fulfill`

```json
{
	"tx_hash": "<transaction hash>",
	"signature": "<signature>"
}
```

`signature` is required when the destination network is Bitcoin. It is a hex-encoded Ed25519 signature made with the resolver's registered fulfillment key. The signed bytes are the decoded transaction hash followed by the intent UUID's 16 raw bytes, with no separator. The hash bytes stay in the order supplied in `tx_hash`.

For other destination networks, `signature` is optional. Success returns HTTP `200` with `estimated_verification_time`, an estimate in seconds.

### `POST /v1/intents/{id}/add-swap`

Reports an optimized single-chain swap:

```json
{ "tx_hash": "<transaction hash>" }
```

Success returns HTTP `200` with an empty body.

### `POST /v1/intents/batch/withdraw`

Reports a withdrawal transaction for one or more intents:

```json
{
	"tx_hash": "<transaction hash>",
	"intent_ids": ["8a2d3f92-2a2b-4e4c-9d8a-3c9f92e4a111"]
}
```

Success returns HTTP `200` with an empty body. The deposit-reporting endpoint returns `fulfillment_deadline` as a Unix timestamp in seconds.

## Secret retrieval

### `GET /v1/intents/{id}/reveal-secret`

```json
{ "secret": "<0x-prefixed 32-byte secret>" }
```

### `POST /v1/intents/batch/reveal-secrets`

Request:

```json
{ "intent_ids": ["<uuid>"] }
```

Response:

```json
{ "secrets": { "<uuid>": "<secret>" } }
```

The single-secret endpoint requires `Fulfilled` status. Batch retrieval fails if any requested intent is not fulfilled.

## Health

### `GET /v1/system/live`

Requires a resolver `X-API-Key`. Success returns HTTP `200` with an empty body. The handler checks liveness, not dependency readiness. A missing or malformed header returns HTTP `400` with error code `14`. An inactive key returns HTTP `401` with code `53`.
