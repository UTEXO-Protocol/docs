Utexo sends lifecycle events to the resolver's configured webhook URL. Transaction reporting uses the separate [Protocol API](/product-suite/swap/resolver-integration/protocol-api).

## Envelope

Each event has a `type` and `data`. `IntentAssigned` nests its payload under `data.intent`:

```json
{
	"type": "IntentAssigned",
	"data": {
		"intent": {
			"id": "8a2d3f92-2a2b-4e4c-9d8a-3c9f92e4a111"
		}
	}
}
```

This example shows only the nesting and intent ID. The assignment fields are listed below.

## Signature verification

Each request carries these headers:

| Header | Value |
| --- | --- |
| `X-Signature` | `0x`-prefixed hex encoding of a 64-byte Ed25519 signature. |
| `X-Timestamp` | Unix timestamp in seconds, encoded as a decimal string. |

The signed bytes are the UTF-8 timestamp header followed by the raw request body, with no separator. The verification key comes from `GET /v1/resolvers/webhooks/public-key` and is a `0x`-prefixed 32-byte Ed25519 public key.

Verification uses the raw body before JSON parsing. JSON re-serialization can change the signed bytes. A resolver rejects invalid signatures and applies its own timestamp freshness and replay policy.

Retries can repeat an event. Lifecycle handling is idempotent by event type and intent identifier. `IntentAssigned` uses `data.intent.id`; most other events use `data.intent_id`.

## IntentAssigned

The `data.intent` object contains `id`, `secret_hash`, `user_source_address`, `user_destination_address`, `user_approval`, `fulfillment_signature`, `fulfillment_request`, `deadline`, `quote_id`, `swap_type`, `cosign_transaction`, `deposit_type`, and `signature_details`.

`deadline` is an RFC 3339 timestamp. `user_approval` has `approval_mechanism` and `data`, rather than `params_to_sign`. `signature_details` contains `signature` and `public_key`.

This webhook expects a JSON response containing `status`. An accepted assignment responds with:

```json
{ "status": "Accepted" }
```

A declined assignment can include details:

```json
{
	"status": "Declined",
	"decline_details": {
		"error_code": 1,
		"message": "quote expired"
	}
}
```

Other lifecycle webhooks require a successful HTTP response and do not require a JSON body.

## DepositConfirmed

The `data` object contains `intent_id`, `deposit_tx`, `fulfillment_deadline`, `fulfillment_signature`, `cosign_transaction`, `fulfillment_request`, and `flow_kind`.

`fulfillment_deadline` is a Unix timestamp in seconds. `flow_kind` is `Permit` or `UserBroadcast`.

`fulfillment_request` contains `intent_id`, `user_destination_address`, `to_token`, `min_amount`, `max_amount`, and `deadline`. Amounts are decimal integer strings. Its deadline is in seconds.

This event authorizes destination-chain fulfillment after the source deposit is confirmed. Fulfillment reporting uses `POST /v1/intents/{id}/fulfill`.

For user-broadcast intents the event `type` is `UserDepositConfirmed` instead of `DepositConfirmed`, but the `data` has the same structure.

## FulfillmentConfirmed

The `data` object contains `intent_id` and `fulfill_tx`. It records confirmation of the destination transaction.

## WithdrawReady

The `data` object contains `intent_id` and `merkle_root`:

```json
{
	"type": "WithdrawReady",
	"data": {
		"intent_id": "8a2d3f92-2a2b-4e4c-9d8a-3c9f92e4a111",
		"merkle_root": "<0x-prefixed 32-byte secret>"
	}
}
```

The current wire field is named `merkle_root`, but its value is the revealed secret. The payload has no `secret` field. The [secret-retrieval endpoints](/product-suite/swap/resolver-integration/protocol-api#secret-retrieval) return the same value under `secret` or `secrets`.

Withdrawal reporting uses `POST /v1/intents/batch/withdraw`.

## SwapConfirmed

The `data` object contains `intent_id`, `flow_kind`, and `swap_tx`. This event marks completion of an optimized single-chain swap.

## RefundInProgress

The `data` object contains `intent_id` and `tx_hash`. A refund transaction is in progress.

## RefundConfirmed

The `data` object contains `intent_id` and `refund_tx`. The refund is confirmed. Fulfillment attempts for the intent must stop.

## FailedTransactionUpdate

The `data` object contains `timestamp`, `tx_hash`, and `intent_ids`. It identifies a failed transaction and the affected intents.

## CalldataValidationFail

The `data` object contains `intent_id` and `error`. It reports rejected transaction data from the resolver.

## Delivery

Failed deliveries are stored for retry. The signed timestamp reflects each delivery attempt.

`TransactionUpdate` and `DepositInfo` are WebSocket messages and are not sent as webhooks.
