Utexo calls the URLs configured for each resolver. The callbacks have no prescribed paths. Requests do not carry an `X-API-Key` header. Each request carries an `X-Request-ID` for correlation.

## Health callback

Utexo sends a `GET` request. The response is:

```json
{ "ok": true }
```

## Quote callback

Utexo sends a `POST` request with these fields:

| Field | Type | Description |
| --- | --- | --- |
| `source_chain`, `dest_chain` | integer | Utexo network IDs. |
| `source_token`, `dest_token` | string | Token identifiers. |
| `source_amount` | string | Amount in whole-token units, such as `"1.5"`. |
| `slippage_tolerance_bps` | string | Integer basis points from `"0"` through `"10000"`. |
| `swap_type` | string | `standard` or `optimized`. |
| `affiliate_id` | string | Affiliate UUID. |
| `retail_user_id` | string or null | Retail user identifier. |
| `user_meta` | JSON value or null | Metadata from the affiliate request. |
| `affiliate_fees` | object or null | Sub-affiliate IDs mapped to `fee_bps`, `network_id`, and `token`. |
| `deposit_type` | string | `escrowed` or `direct`. |
| `flow_kind` | string | `Permit` or `UserBroadcast`. |

The callback uses `source_amount` and `slippage_tolerance_bps`. The affiliate quote endpoint uses `amount` and `slippage_bps`.

### Response

```json
{
	"id": "19b44362-bc4d-4b2e-824f-f712c6c80eff",
	"source_chain": 1,
	"source_token": "0xc02aaa39b223fe8d0a0e5c4f27ead9083c756cc2",
	"dest_chain": 4,
	"dest_token": "So11111111111111111111111111111111111111112",
	"intermediate_token": null,
	"intermediate_token_amount_min": null,
	"intermediate_token_amount_max": null,
	"intermediate_token_decimals": null,
	"source_amount_lots": "1000000000000000000",
	"source_amount_decimals": 18,
	"source_amount_in_usd": "2000",
	"min_dest_amount_lots": "19900000000",
	"max_dest_amount_lots": "20000000000",
	"dest_amount_decimals": 9,
	"dest_amount_in_usd": "1990",
	"expiry": 1793700000000,
	"affiliate_fees": null
}
```

Lot amounts are decimal integer strings. `expiry` is a Unix timestamp in milliseconds. The USD fields accept numeric strings or JSON numbers and default to `0` when omitted.

Each non-null `affiliate_fees` entry includes `fee_bps`, `network_id`, `token`, `fee_amount_lots`, and `fee_amount_decimals`. Intermediate-token bounds are required together when an intermediate token is present.

### Errors

Non-success responses use this envelope:

```json
{
	"error_code": 1,
	"msg": "swap amount is below the minimum threshold",
	"details": { "min_amount": "0.01" }
}
```

`details` is optional. The quote callback has a 600 ms request timeout.

| Code | Constant |
| --- | --- |
| `0` | `INTERNAL_SERVER_ERROR` |
| `1` | `SWAP_AMOUNT_TOO_SMALL` |
| `2` | `SWAP_AMOUNT_TOO_LARGE` |
| `3` | `UNSUPPORTED_SOURCE_NETWORK` |
| `4` | `UNSUPPORTED_DEST_NETWORK` |
| `5` | `UNSUPPORTED_SOURCE_TOKEN` |
| `6` | `UNSUPPORTED_DEST_TOKEN` |
| `7` | `INVALID_SLIPPAGE_TOLERANCE_BPS` |

## Resolver address callback

The `POST` request contains `intent_id`, `chain`, and `address_type`. `chain` is a Utexo network ID. `address_type` is `Deposit` or `Withdraw`.

```json
{ "address": "<resolver address>" }
```

## Bitcoin deposit PSBT callback

The `POST` request contains `intent_id`, `quote_id`, `protocol_pub_key`, `user_address`, `user_pub_key`, `secret_hash`, and `deadline`.

`secret_hash` is double SHA-256. `deadline` is a Unix timestamp in seconds. The request has no `deposit_type` field.

The response is:

```json
{
	"psbt": "cHNidP8...",
	"x_only_public_key": "<resolver x-only public key>",
	"refund_control_block": "<hex>",
	"fast_refund_control_block": "<hex>"
}
```

The three Taproot metadata fields are required for escrowed deposits and are `null` for direct deposits. The resolver obtains the deposit type from its quote.

RGB sources use the [user-broadcast transaction callback](#user-broadcast-transaction-callback).

## Solana cosign callback

The `POST` request uses these fields:

| Field | Type |
| --- | --- |
| `request_type` | `DepositSwap`, `Fulfill`, or `WithdrawToUser` |
| `intent_id`, `quote_id`, `resolver_id` | UUID string |
| `user_address`, `resolver_deposit` | Base58 address |
| `token_in`, `token_out` | Token identifier |
| `secret_hash` | Hex string |
| `nonce` | integer |
| `amount_in`, `min_amount_out`, `max_amount_out` | Decimal integer string |
| `deadline` | Unix timestamp in seconds |
| `intermediate_token_out` | string or null |
| `intermediate_min_amount_out`, `intermediate_max_amount_out` | Decimal integer string or null |
| `swap_type` | `standard` or `optimized` |
| `recent_blockhash` | string or null |
| `deposit_type` | `escrowed` or `direct` |
| `flow_kind` | `Permit` or `UserBroadcast` |

The response contains a hex-encoded serialized versioned transaction:

```json
{ "transaction": "<hex>" }
```

Signer positions follow the transaction message. Existing signatures remain valid only while that message remains unchanged.

## User-broadcast transaction callback

The `POST` request contains these fields:

| Field | Description |
| --- | --- |
| `intent_id`, `quote_id`, `affiliate_id` | UUID strings. |
| `user_source_address`, `user_destination_address`, `refund_address` | User addresses. |
| `deadline` | RFC 3339 timestamp. |
| `nonce` | Integer nonce. |
| `secret_hash` | Hex-encoded hash. |
| `psbt_data` | For Bitcoin, an object with `protocol_pub_key` and `user_source_pub_key`. Otherwise, `null`. |

The response contains `intent_id` and a case-sensitive `calldata` variant. A Bitcoin response has this form:

```json
{
	"intent_id": "8a2d3f92-2a2b-4e4c-9d8a-3c9f92e4a111",
	"calldata": {
		"Psbt": {
			"bitcoin_psbt": {
				"psbt": "cHNidP8...",
				"x_only_public_key": "<resolver x-only public key>",
				"refund_control_block": "<hex>",
				"fast_refund_control_block": "<hex>"
			}
		}
	}
}
```

The other variants are `Cosign`, with `transaction`, `recent_blockhash`, and `resolver_deposit_address`, and `EvmLike`, with `transaction` and `resolver_deposit_address`. For `Cosign`, the transaction is hex-encoded serialized Solana data. For `EvmLike`, `transaction` is hex-encoded contract calldata.

For RGB, the resolver returns a `Psbt` template. Utexo derives the witness invoice and returns `deposit_tx_data.RgbLock` to the affiliate. The resolver response has no `RgbLock` variant or `destination_script_hex` field. See [RGB USDT settlement](/product-suite/swap/resolver-integration/rgb-settlement) for the lock template and claim procedure.

## Fast-refund signing callback

The `POST` request contains `intent_id`, `chain`, and `deposit_type`. For Bitcoin, it also contains `btc_data`, an object with `psbt`, `tapscipt`, and `input`.

The wire field is spelled `tapscipt`. `input` is the PSBT input index.

```json
{ "signature": "<hex>" }
```
