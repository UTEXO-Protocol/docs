## Overview

The **Utexo Mint API** is a network-agnostic REST interface for cross-network asset transfers. Clients must discover the networks currently connected to an environment with `GET /networks` instead of hardcoding network availability.

USDT0 settles natively on Arbitrum, which acts as the hub; Ethereum, Polygon PoS, Plasma and Tron reach that hub through USDT0 / LayerZero and the Utexo entrypoint contracts.

<Info>
  **Base URL:** `https://gateway.mint.utexo.com/api/v0`

  All paths in this reference are relative to the base URL. Contact the Utexo team for access to the test environment before launch.

  **Interactive API docs:** [https://gateway.mint.utexo.com/api/v0/docs/](https://gateway.mint.utexo.com/api/v0/docs/)
</Info>

The API is stateless and JSON-based. Every endpoint in this reference needs authentication: an API key in the `X-API-Key` header or a signed-in session cookie (see [Authentication](#authentication)).

## Transfer Flows

The Mint moves USDT in two directions: **lock and mint** (USDT0 on EVM → USDT on Bitcoin) and **burn and unlock** (USDT on Bitcoin → USDT0 on EVM).

<Info>
  **RGB network ID:** take the RGB-side network from `GET /networks`. The Utexo RGB network ID is `827166`. The RGB wallet must support the BFA asset schema; see [RGB wallet requirements](/mint/mint-burn-integration#rgb-wallet-requirements).
</Info>


### Lock and mint: EVM → RGB

<Steps>
  <Step title="Discover networks and tokens">
    `GET /networks` — list the connected networks and take the `id` of the source network and of the RGB network.

    `GET /networks/{network-id}/supported-tokens` — take the token `id` on each side. USDT is the only token bridged today.
  </Step>
  <Step title="Estimate the mint">
    `GET /mint-burn/estimate/{senderNetworkId}/{recipientNetworkId}/{tokenId}/{amount}` — the amount minted on Bitcoin for a gross deposit, and the bridge commission.
  </Step>
  <Step title="Create an RGB invoice">
    The recipient's RGB wallet creates an invoice for the USDT asset.
  </Step>
  <Step title="Prepare the mint">
    `POST /mint/op-id` - submit the invoice, the gross deposit, the source network and the token ID. The response contains the `opId`, the `settlementData` to pass to the deposit, and `ttlSeconds`. If the source network uses an entrypoint contract, the response also contains an `entrypoint` object.
  </Step>
  <Step title="Lock USDT0">
    Before `ttlSeconds` runs out, the user calls `fundsIn()` on the Arbitrum bridge contract with `depositAmount` and passes `settlementData` verbatim as the `settlementData` argument. On a network that uses an entrypoint contract, the user calls that contract with the returned `depositParams` instead. This step happens **client-side**; the API does not broadcast the transaction.
  </Step>
  <Step title="Track the mint">
    `GET /lock/{opId}/status` - poll until the status is `completed` or `expired`.
  </Step>
</Steps>

### Burn and unlock: RGB → EVM

<Steps>
  <Step title="Estimate the release">
    `GET /mint-burn/estimate/{senderNetworkId}/{recipientNetworkId}/{tokenId}/{amount}` — the USDT0 released for a burn of `amount`, and the bridge commission.
  </Step>
  <Step title="Check the release capacity">
    `GET /unlock/capacity/{srcNetworkId}/{networkId}/{tokenId}` — read `available`. A burn cannot be undone, so do not burn more than `available`.
  </Step>
  <Step title="Burn USDT on Bitcoin">
    Burn the amount in the RGB wallet and commit the payout destination: the burn reason is the V1 burn destination hash, on every payout network, and you keep the record for `/unlock` (see [Burn destination](#burn-destination)). Then export the burn consignment from the wallet and base64-encode the raw bytes.
  </Step>
  <Step title="Submit the burn consignment">
    Optionally, `POST /unlock/verify` - dry-run the checks `/unlock` makes before it claims the burn.

    `POST /unlock` - send the base64-encoded consignment, plus `burnDestination` for a V1 burn. Submit it right after the burn: if the burn is not final on Bitcoin yet, the response is `confirming` and the bridge sends the release itself once it is.
  </Step>
  <Step title="Confirm the release">
    The response contains the `status`, the `evmTxHash` of the submitted release (empty while `confirming`), the `recipient` read from the burn, and the burn's `operationId`. The release confirms on the EVM network asynchronously.
  </Step>
</Steps>

## Authentication

### API key or session

Every endpoint in this reference needs one of:

- **API key:** the `X-API-Key` header. Send exactly one key; two headers return `400`.
- **Session:** the customer session cookie set by signing in to the Utexo web app. Browser requests other than `GET` also need `X-Requested-With: XMLHttpRequest` and a trusted origin.

A missing or invalid key or session returns `401`.

The API key is self-service. Sign in, complete KYC or KYB, and call `POST /users/me/api-key` from the signed-in session. The response (`201`) contains `apiKey` and `createdAt`; the raw key is returned only this once. `GET /users/me/api-key` returns only `createdAt`, and `DELETE /users/me/api-key` revokes the key. Keep the key on a trusted backend: do not embed it in a browser app or an untrusted wallet.

### Verification and the mint limit

An account without approved KYC or KYB can mint only up to a cumulative limit set by Utexo, which can change: the new gross deposit plus its completed and active mint deposits must stay within it. Above it, `GET /mint-burn/estimate` (for a mint) and `POST /mint/op-id` return `403` with code `9`. Burns do not count against the limit. `GET /users/me` (session only) shows `kycStatus`, `kybStatus` and the allowance in `mintBurnLimit` (`max`, `used`, `reserved`, `free`, `unlimited`).

```bash
curl -X POST https://gateway.mint.utexo.com/api/v0/mint/op-id \
  -H "X-API-Key: <API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"networkId": 827166, "sourceNetworkId": 42161, "tokenId": 2, "invoice": "rgb:...", "amount": 1000000}'
```

## Endpoints

### Networks

#### `GET /networks` — List Connected Networks

Returns all connected networks. Optionally filter by token, source network, or name.

**Query Parameters**

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `token-id` | `integer` | No | Filter results to networks that support this token ID. Cannot be combined with `source-network-id`. |
| `source-network-id` | `integer` | No | Return networks supported by the specified source network. Cannot be combined with `token-id`. |
| `search` | `string` | No | Filter results by network name (partial match) |

**Response `200`** — Array of `Network` objects

```json
[
  {
    "id": 42161,
    "name": "ARBITRUM-ONE",
    "displayName": "Arbitrum One",
    "type": "NT_EVM",
    "bridgeContract": "0x...",
    "gasLimit": 200000,
    "iconLink": "https://...",
    "active": true,
    "explorerBaseUrl": "https://arbiscan.io"
  }
]
```

Returns a paginated list of tokens supported on a given network. If `token-id` is provided as a query parameter, returns a single `Token` object instead of a paginated response.

**Path Parameters**

| Parameter | Type | Required | Description |

| `network-id` | `integer` | Yes | The network ID |

**Query Parameters**

| Parameter | Type | Required | Description |

| `search` | `string` | No | Filter tokens by name or symbol |
| `limit` | `integer` | No | Number of results per page |
| `page` | `integer` | No | Page number (1-indexed) |

**Response `200`** — `SupportedTokensResponse`

```json
{
  "tokens": [...],
  "limit": 20,
  "offset": 0,
  "pageCount": 3,
  "currentPage": 1,
  "totalCount": 45

```

**Path Parameters**

| Parameter | Type | Required | Description |

### Mint and burn

#### `GET /mint-burn/estimate/{senderNetworkId}/{recipientNetworkId}/{tokenId}/{amount}` — Estimate a Mint or Burn

Quotes what a mint or a burn receives and what the bridge charges. The direction follows from which side is the RGB network. Requires authentication.

**Path Parameters**

| Parameter | Type | Description |
| --- | --- | --- |
| `senderNetworkId` | `integer` | Network the funds leave: the EVM network for a mint, the RGB network for a burn |
| `recipientNetworkId` | `integer` | Network the funds arrive on |
| `tokenId` | `integer` | Token ID on the EVM network |
| `amount` | `integer` | Gross amount in base units: the deposit for a mint, the burned amount for a burn |

**Query Parameters**

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `senderAddress` | `string` | Conditional | Depositor address. Required for a mint from an entrypoint network, or with an `opId` whose mint stored a depositor |
| `opId` | `string` | No | An unpaid mint you already prepared (64 hex characters). Rechecks its fees without counting its reservation twice. It must belong to you and match the route, token, depositor and exact gross amount |

**Response `200`**

```json
{
  "receiveAmount": "98950",
  "totalTokenCommission": "1050",
  "totalTokenFee": "1050",
  "percentFee": "1000",
  "baseFee": "50",
  "minAmount": "100000",
  "transactionCost": "1050"
}
```

All amounts are decimal strings in base units. `amount = receiveAmount + totalTokenFee` on every route.

<Note>
  The amounts above are an example. Fees are set per route and change over time, so always read them from the estimate.
</Note>

| Field | Description |
| --- | --- |
| `receiveAmount` | What arrives: minted on Bitcoin for a mint, delivered on the recipient network for a burn, after the OFT's fee on a LayerZero leg |
| `totalTokenCommission` | The whole bridge commission in the token: `percentFee` plus `baseFee` |
| `totalTokenFee` | Everything kept from `amount` in the token: `totalTokenCommission` plus `oftFee`. Equals `totalTokenCommission` on a direct route |
| `percentFee` | Percentage part of the commission |
| `baseFee` | Flat part of the commission |
| `minAmount` | The bridge contract's floor for the route: `minFundsInAmount` for a mint, `minFundsOutAmount` for a burn. Read live |
| `oftFee` | What the USDT0 OFT keeps on a LayerZero leg, in token base units. Omitted on a direct route |
| `lzNativeFee` | LayerZero messaging fee in the paying chain's native base units: paid by the depositor on a mint, by the bridge on a burn. Never deducted. Omitted on a direct route |
| `networkFee` | The depositor's gas for a mint, in native base units, including `approveNetworkFee`. Omitted on a burn and when it cannot be measured |
| `approveNetworkFee` | The part of `networkFee` that pays a token approval still needed. Omitted when the allowance covers the amount |
| `networkFeeInToken` | `networkFee` valued in the token. Omitted on a burn or when the rate is unavailable |
| `lzNativeFeeInToken` | `lzNativeFee` valued in the token, for a mint. Omitted on a direct route, on a burn, or when the rate is unavailable |
| `transactionCost` | Everything the user pays, in token base units: `totalTokenFee` plus the `InToken` values that are present |
| `estimatedDeliverySeconds` | Median delivery time of the route's latest completed transfers (last 14 days). Omitted while fewer than 3 have completed |
| `estimatedDeliverySecondsP90` | 90th percentile of the same transfers |

**Error Responses**

| Status | Meaning |
| --- | --- |
| `400` | Invalid IDs or amount, a network pair that is not a mint or a burn, an unsupported token, a missing `senderAddress` on an entrypoint mint, or a malformed or mismatched `opId`. An amount below the route's floor returns code `2` with `details` (`amount`, `minAmount`) |
| `401` | The API key or session is missing or invalid |
| `403` | Code `9`: for a mint, KYC or KYB is required because the cumulative mint limit would be exceeded |
| `404` | The RGB network is not served |
| `409` | Code `12`: the prepared mint named by `opId` is no longer payable. Check its status before starting another mint |
| `503` | The commission for this route cannot be priced, it is charged in the native token, or the LayerZero delivery of a burn cannot be quoted |

#### `POST /mint/op-id` — Prepare a Mint

Prepares the RGB side of a lock-and-mint transfer and returns the data the deposit must carry. It does not move tokens or submit the EVM transaction. Requires authentication. For an account without KYC or KYB, the gross deposit counts against the [mint limit](#verification-and-the-mint-limit).

**Request Body**

```json
{
  "networkId": 827166,
  "sourceNetworkId": 42161,
  "tokenId": 2,
  "invoice": "rgb:...",
  "amount": 1000000
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `networkId` | `integer` | Yes | RGB network ID (not the EVM source chain) |
| `sourceNetworkId` | `integer` | Yes | EVM network the deposit is sent from |
| `sourceAddress` | `string` | No | Address that sends the deposit. Required when the source network uses an entrypoint contract |
| `tokenId` | `integer` | Yes | Token ID of the deposited token on the source network |
| `assetId` | `string` | No | RGB asset ID. Omit to use the standard USDT asset |
| `invoice` | `string` | Yes | Invoice created by the recipient's RGB wallet |
| `amount` | `integer` | Yes | Gross deposit in token base units. For a 6-decimal token, `1000000` is 1 USDT. The bridge takes its commission from it and mints the rest |

**Response `200`**

```json
{
  "opId": "9f2c...e41a",
  "ttlSeconds": 1800,
  "settlementData": "0x9f2c...e41a",
  "depositAmount": "1000000",
  "mintAmount": "<deposit less commission>"
}
```

| Field | Description |
| --- | --- |
| `opId` | RGB operation ID of the mint. Use it to track the mint |
| `ttlSeconds` | Time available to submit the matching deposit |
| `settlementData` | ABI-encoded `opId`. Pass it verbatim as the `settlementData` argument of `fundsIn()`; do not pass `opId` directly |
| `depositAmount` | Gross deposit in base units: the amount `fundsIn()` transfers |
| `mintAmount` | Amount minted on Bitcoin, in base units: the deposit less the bridge commission |
| `entrypoint` | Present only when the source network uses an entrypoint contract: `contractAddress`, `depositParams` (`amountLD`, `minAmountLD`, `extraOptions`, `payload`, `refundTo`, `expectedComposeValue`), `networkFee`, `nativeFee` and `totalNativeRequired` |

The `fundsIn` must be included in a block before `ttlSeconds` runs out. Sending the same request again for a prepared mint that is not paid yet resumes it; a retry never renews the original deadline.

**Error Responses**

| Status | Meaning |
| --- | --- |
| `400` | Invalid network, amount, invoice, asset or transport endpoint. A deposit below the bridge's `minFundsInAmount` (for a LayerZero mint, a delivery below it) returns code `2` with `details` |
| `401` | The API key or session is missing or invalid |
| `403` | Code `9`: KYC or KYB is required because the cumulative mint limit would be exceeded |
| `409` | The invoice is already used or belongs to another preparation, its owner, wallet, route, token or amount differs from the original, payment was already observed, too little time is left to resume safely, or the unpaid-mint limit is reached |
| `429` | Rate limit exceeded |
| `500` | Mint preparation failed inside the bridge or RGB connector |
| `501` | The connector does not support mint preparation |
| `503` | The connector is unavailable, the commission cannot be priced or is in the native token, or another mint on the wallet is not broadcast yet. Code `11`: the mint wallet has no bridge right to spare; retry the same request later |

#### `GET /lock/{opId}/status` — Get Mint Status

Returns the state of a prepared mint. Poll it after the deposit is submitted. Requires authentication. Returns `404` for an unknown `opId`.

**Response `200`**

```json
{
  "opId": "9f2c...e41a",
  "status": "broadcast",
  "expiresAt": "2026-10-06T12:30:00Z",
  "evmTxHash": "0xabc..."
}
```

| Status | Description |
| --- | --- |
| `awaiting_funds_in` | Waiting for the deposit. `expiresAt` is the deadline for the `fundsIn` block timestamp: a `fundsIn` included by then still moves to `funds_in_confirmed` once confirmed |
| `funds_in_confirmed` | The deposit was detected and matched to the mint |
| `bridge_signed` | The mint signer signed the mint |
| `broadcast` | The Bitcoin transaction anchoring the mint was broadcast |
| `completed` | The Bitcoin transaction has the required confirmations; the mint is complete |
| `expired` | No matching deposit arrived in time |

`evmTxHash` is the detected deposit transaction on the EVM network. It is omitted until the deposit is detected.

#### `GET /unlock/capacity/{srcNetworkId}/{networkId}/{tokenId}` — Get Release Capacity

Returns how much can be released right now for a burn. Call it before you burn. Requires authentication.

**Path Parameters**

| Parameter | Type | Description |
| --- | --- | --- |
| `srcNetworkId` | `integer` | RGB network where the USDT is burned |
| `networkId` | `integer` | EVM network where USDT0 is released |
| `tokenId` | `integer` | Token ID on the EVM network |

**Response `200`**

```json
{
  "srcNetworkId": 827166,
  "networkId": 42161,
  "tokenId": 2,
  "poolBalance": "1354199",
  "pendingReleases": "0",
  "availableOutflow": "135419",
  "available": "135419"
}
```

| Field | Description |
| --- | --- |
| `poolBalance` | USDT0 locked in the bridge, in base units |
| `pendingReleases` | Amount reserved by releases still in progress, burns accepted as `confirming` included |
| `availableOutflow` | Remaining outflow allowance; omitted when no limit applies |
| `available` | Maximum amount that can be burned and released now |

#### `POST /unlock` — Release After a Burn

Validates a burn consignment, gets the release signatures and submits the EVM release. The amount and the payout destination are read from the burn itself; the request cannot change them. Requires authentication. Burns do not count against the mint limit.

Submit right after the burn. The signer enclaves require 6 Bitcoin confirmations of the burn before they sign; if the burn is not final yet, the bridge accepts it as `confirming` and sends the release itself once it is.

**Request Body**

```json
{
  "consignment": "<base64-encoded burn consignment>",
  "srcNetworkId": 827166,
  "destinationNetworkId": 137,
  "tokenId": 5,
  "burnDestination": {
    "version": 1,
    "destinationChainId": 137,
    "dstEid": 30109,
    "recipient": "0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266"
  }
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `consignment` | `string` | Yes | Complete burn consignment, standard base64 |
| `destinationNetworkId` | `integer` | Yes | Network of the release |
| `srcNetworkId` | `integer` | No | RGB network of the burn. Optional when the bridge serves one RGB network |
| `tokenId` | `integer` | Conditional | Payout token ID. Required for a destination reached through USDT0 / LayerZero |
| `maxFeeRate` | `string` | No | Cap on the EVM gas price in wei. Omitted or `"0"` leaves the cap to the bridge |
| `burnDestination` | `object` | Yes | The V1 burn destination record whose hash the burn commits. See [Burn destination](#burn-destination) |

**Response `200`**

```json
{
  "evmTxHash": "0xabc...",
  "status": "submitted",
  "recipient": "0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266",
  "operationId": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
}
```

| Field | Description |
| --- | --- |
| `status` | `submitted`: the EVM release was sent. `confirming`: the burn is accepted but not final on Bitcoin; nothing was sent, and the bridge sends the release itself once it is. Do not resend |
| `evmTxHash` | The submitted release transaction. Empty while `confirming`. For a LayerZero destination, this is the Arbitrum transaction |
| `recipient` | Payee: the `recipient` of the V1 record |
| `operationId` | keccak256 of the consignment, hex |

A burn whose release does not go out within 24 hours (for example, a replaced or dropped burn transaction) can be unlocked again.

**Error Responses**

| Status | Meaning |
| --- | --- |
| `400` | Invalid input; an unknown `tokenId`, or none for a LayerZero destination; a consignment that is not a burn, or a burn without a burn reason; a `burnDestination` that is missing, malformed, does not hash to the burn reason, or is for another destination; an asset the bridge does not release; or code `4`, the release exceeds the current outflow allowance (the burn stays redeemable; retry later) |
| `401` | The API key or session is missing or invalid |
| `404` | Unknown `destinationNetworkId` or `srcNetworkId`, or the burn cites a mint this bridge never prepared |
| `409` | The burn was already released or is being released (`confirming` included). Codes `6`, `7`, `8`: the bridge could not keep the burn waiting for Bitcoin finality; nothing was sent, retry the same request later |
| `422` | Code `10`: the asset's reject list rejects a coin the burn descends from. Do not retry |
| `429` | Rate limit exceeded |
| `500` | Burn validation, signing or EVM submission failed |

#### Burn destination

A burn commits its payout target in the 32-byte burn reason: `hash_v1` of a V1 burn destination record. The bridge releases it with a direct `fundsOut` on Arbitrum (`dstEid` `0`) or with `lzFundsOut` to a LayerZero endpoint. Send the record as `burnDestination`.

<Warning>
  Keep the V1 record: a burn cannot be released without it.
</Warning>

| Record field | Type | Rule |
| --- | --- | --- |
| `version` | `integer` | Always `1` |
| `destinationChainId` | `integer` (uint64) | Must equal `destinationNetworkId`. Not `0` |
| `dstEid` | `integer` (uint32) | LayerZero endpoint ID of the destination. `0` means a direct `fundsOut` on Arbitrum |
| `recipient` | `string` | Chain-native payee, `0x` hex, 1 to 32 bytes. Exactly 20 bytes when `dstEid` is `0` |

```text
TYPEHASH_V1 = keccak256("UtexoBurnDestinationV1(uint64 destinationChainId,uint32 dstEid,bytes recipient)")
            = 0xa1cba9d766975eb04c6a31c3b68dbb2381444a222c9972b6bf3ab26fcb829b00
hash_v1     = keccak256(abi.encode(TYPEHASH_V1, uint64 destinationChainId, uint32 dstEid, keccak256(recipient)))
```

Routes used by the Utexo web app (confirm them for your environment):

| Destination | `destinationChainId` | `dstEid` | `recipient` |
| --- | ---: | ---: | --- |
| Arbitrum One | `42161` | `0` | 20-byte EVM address |
| Ethereum | `1` | `30101` | 20-byte EVM address |
| Polygon PoS | `137` | `30109` | 20-byte EVM address |
| Plasma | `9745` | `30383` | 20-byte EVM address |
| Tron | `728126428` | `30420` | 21-byte Tron address (Base58Check decoded, checksum removed, starts with `0x41`) |

See [Mint and Burn Integration](/mint/mint-burn-integration#choose-the-burn-destination) for a worked example and a test vector.

#### `POST /unlock/verify` - Check a Burn Before Unlocking

Takes the same body as `POST /unlock` and runs the checks `POST /unlock` makes before it claims the burn: the consignment is a burn, the asset is the bridged RGB asset, the burn reason is the hash of the `burnDestination` sent for this destination, and the outflow capacity covers the amount. Nothing is claimed, signed or sent, so it can be repeated. It does not check Bitcoin finality, the deposits behind the cited mints, or the reject list. Requires authentication.

**Response `200`**

```json
{
  "operationId": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
  "amount": "300000",
  "recipient": "0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266",
  "assetId": "rgb:...",
  "burnTxid": "d4d4...d4d4"
}
```

| Field | Description |
| --- | --- |
| `operationId` | keccak256 of the consignment; `POST /unlock` returns the same ID |
| `amount` | Burned amount in base units, before the bridge commission |
| `recipient` | Payee of the release |
| `assetId` | Burned RGB asset |
| `burnTxid` | Bitcoin transaction anchoring the burn |

Errors are as for `POST /unlock`: `400` (code `4` for outflow capacity), `401`, `404`, `409` (already redeemed or being redeemed), `429`, `500`.

## Error Responses

All endpoints return a consistent error envelope on failure.

```json
{
  "error": "human-readable error message",
  "code": 1
}
```

**Error Codes**

| Code | Meaning |
| --- | --- |
| `1` | RGB protocol error |
| `2` | An amount the caller must change, for example a mint or burn below the route's minimum (`details`: `amount`, `minAmount`) |
| `3` | System balance error (the bridge cannot cover the transfer) |
| `4` | Destination outflow limit exceeded. Retry after capacity recovers |
| `5` | AML policy or clearance failure |
| `6` | Release wait: the Bitcoin relay has not reached the burn block yet |
| `7` | Release wait: the burn does not have enough Bitcoin confirmations yet |
| `8` | Release wait: the on-chain verifier refused the relay depth or freshness |
| `9` | KYC or KYB is required: the cumulative mint limit would be exceeded (HTTP `403`) |
| `10` | The asset's reject list rejects a coin the burn descends from (HTTP `422` from `POST /unlock`). Do not retry |
| `11` | The mint wallet has no bridge right to spare (HTTP `503` from `POST /mint/op-id`). Retry later |
| `12` | The prepared mint is no longer payable (HTTP `409` from the estimate with `opId`). Do not pay it |
| `65535` | Other / unclassified error |

Codes `6`, `7` and `8` come with HTTP `409` from `POST /unlock`, and a `details` object with the numbers behind the wait (for example `confirmations` and `requiredConfirmations` for code `7`). A burn waiting for finality is normally accepted as `confirming` instead, so these codes are returned only when the bridge could not keep it waiting. Nothing is sent to the EVM network, and the burn stays redeemable. Authentication errors may omit `code`.

## Glossary

| Term | Definition |
| --- | --- |
| **RGB** | A client-side validated smart contract protocol built on Bitcoin. Assets are issued and transferred using Bitcoin UTXOs as state anchors. |
| **RGB Invoice** | A blinded payment request string used to receive RGB assets. Contains blinded UTXO data to preserve receiver privacy. |
| **EVM** | Ethereum Virtual Machine — the execution environment used by Arbitrum and other compatible chains. |
| **Bridge Contract** | The EVM smart contract that locks or releases assets on the EVM side of a cross-chain transfer. |
| **`fundsIn()`** | The method on the EVM bridge contract the sender calls to deposit assets for minting. |
| **OpId** | The RGB operation ID of a prepared mint, returned by `POST /mint/op-id`. |
| **settlementData** | The ABI-encoded OpId the deposit carries to bind it to the prepared mint. |
| **Burn consignment** | The RGB data that proves a burn. `POST /unlock` reads the release amount and recipient from it. |
| **Entrypoint contract** | A per-network contract that forwards a deposit to the Arbitrum hub through LayerZero. When a route uses it, `POST /mint/op-id` returns an `entrypoint` object and the user calls that contract instead of `fundsIn()`. |
| **UTXO** | Unspent Transaction Output — the fundamental unit of Bitcoin accounting. RGB asset state is anchored to UTXOs. |
