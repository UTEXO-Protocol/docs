This guide is for partners that run mint and burn from their own backend, such as wallets, exchanges, and resolvers that rebalance between USDT or USDT0 on EVM networks and USDT on Bitcoin.

The Mint supports two directions:

- **Lock and mint:** lock USDT or USDT0 and mint the net amount as USDT on Bitcoin to an RGB wallet.
- **Burn and unlock:** burn USDT on Bitcoin and unlock the net amount as USDT or USDT0 to the EVM address committed in the burn.

## Supported networks and routes

The bridge holds its mint and burn liquidity on **Arbitrum One**. A mint from Arbitrum calls the bridge contract directly. A mint from another supported source network first deposits into a Utexo entrypoint contract, which forwards the funds to the Arbitrum bridge before the RGB mint is executed. A burn is always released from the Arbitrum bridge: to Arbitrum directly, or to another supported network through USDT0 / LayerZero.

| Network | Network ID | Role in this guide | Deposit path |
| --- | ---: | --- | --- |
| Utexo RGB | `827166` | Mint destination and burn source | RGB/BFA |
| Arbitrum One | `42161` | Direct mint source and burn destination | Direct bridge contract call |
| Ethereum | `1` | Mint source and burn destination | Utexo entrypoint (mint); USDT0 / LayerZero release (burn) |
| Polygon PoS | `137` | Mint source and burn destination | Utexo entrypoint (mint); USDT0 / LayerZero release (burn) |
| Plasma | `9745` | Mint source and burn destination | Utexo entrypoint (mint); USDT0 / LayerZero release (burn) |
| Tron | `728126428` | Mint source and burn destination | Utexo entrypoint (mint); USDT0 / LayerZero release (burn) |

<Note>
  The network IDs above are part of the bridge API contract. Contract addresses, token IDs, and operational availability are deployment-specific; obtain those values from `GET /networks` and `GET /networks/{networkId}/supported-tokens` in the target environment.
</Note>

<Info>
  **Base URL (staging):** `https://transfer.gateway.stage.utexo.com/api/v0`

  Every endpoint in this guide requires authentication. Create an account, complete KYC or KYB, and generate an API key in your account. Contact the Utexo team for production access.
</Info>

## Before you start

You need:

- **An API key.** Every endpoint in this guide, including `GET /networks`, the estimate, and the capacity endpoint, requires the `X-API-Key` header (or a signed-in session cookie). A missing or invalid key returns `401`. Generate the key yourself, from a signed-in session, with `POST /users/me/api-key` after your account has passed KYC or KYB. The raw key (`apiKey`) is returned only once, when it is created. `GET` on the same path returns only its creation time, and `DELETE` revokes it. Keep the key on your backend. Do not put it in a browser app or a wallet you do not control.
- **Verification for larger mints.** An account that has not completed KYC or KYB can mint only up to a cumulative limit set by Utexo: the new gross deposit plus its completed and active mint deposits must stay within it. Above the limit, the estimate and `POST /mint/op-id` return `403` with code `9`. Burns do not count against this limit.
- **An account on the source network** with the supported USDT or USDT0 token and native currency for gas or fees. A direct Arbitrum mint also requires ETH. Ethereum, Polygon PoS, Plasma, and Tron use a Utexo entrypoint contract; see [Deposit from another network](#deposit-from-another-network).
- **An RGB wallet that supports the BFA asset schema.** See [RGB wallet requirements](#rgb-wallet-requirements).
- **Bitcoin for wallet operations.** The receiving wallet needs confirmed sats to create RGB-colorable UTXOs. A burn also needs an empty colorable UTXO and enough sats for its Bitcoin transaction fee.

All API and wallet amounts in this guide are integers in token base units. USDT and USDT0 have 6 decimals, so `1000000` is 1 USDT.

### Find the network and token IDs

```bash
curl -H "X-API-Key: <API_KEY>" https://transfer.gateway.stage.utexo.com/api/v0/networks
curl -H "X-API-Key: <API_KEY>" "https://transfer.gateway.stage.utexo.com/api/v0/networks/<SOURCE_NETWORK_ID>/supported-tokens"
curl -H "X-API-Key: <API_KEY>" https://transfer.gateway.stage.utexo.com/api/v0/networks/827166/supported-tokens
```

From the responses, take:

| Value | Where | Used in |
| --- | --- | --- |
| RGB network ID | Utexo protocol network ID (`827166`) | `networkId` of `/mint/op-id`, `recipientNetworkId` of the mint estimate, `srcNetworkId` of `/unlock` |
| EVM network ID | `GET /networks`, for example `ARBITRUM-ONE` (`42161`) | `sourceNetworkId` of `/mint/op-id`, `destinationNetworkId` of `/unlock` |
| Bridge contract | `bridgeContract` of the Arbitrum network | The `fundsIn` call and token approval |
| Source token ID and address | `GET /networks/{sourceNetworkId}/supported-tokens`, USDT | `tokenId` of mint and estimate requests; source token approval |
| Arbitrum token ID and address | `GET /networks/42161/supported-tokens`, USDT or USDT0 | `tokenId` of unlock and capacity requests for a release to Arbitrum; direct Arbitrum approval |
| Destination token ID | `GET /networks/{destinationNetworkId}/supported-tokens`, USDT | `tokenId` of unlock, capacity and estimate requests for a release to another network |
| RGB asset ID | `smartContractAddress` of USDT on the Utexo RGB network | The RGB invoice and burn |

Use the protocol network IDs listed above. Discover contract addresses, token IDs, asset IDs, and active route configuration from the environment you are integrating with.

## Estimate the result

Call the estimate endpoint (API key required) before either a mint or a burn:

```text
GET /mint-burn/estimate/{senderNetworkId}/{recipientNetworkId}/{tokenId}/{amount}
```

`amount` is always the **gross input** in base units:

- for a mint, it is the amount deposited on the source network;
- for a burn, it is the amount burned on Bitcoin.

Every successful estimate returns integer base-unit amounts as strings. A direct Arbitrum mint looks like this:

```json
{
  "receiveAmount": "989500",
  "totalTokenCommission": "10500",
  "totalTokenFee": "10500",
  "percentFee": "10000",
  "baseFee": "500",
  "minAmount": "100000",
  "networkFee": "40000000000000",
  "networkFeeInToken": "120000",
  "transactionCost": "130500",
  "estimatedDeliverySeconds": 245,
  "estimatedDeliverySecondsP90": 1476
}
```

`receiveAmount` is what arrives: minted on RGB for a mint, delivered on the recipient network for a burn. It is net of the bridge commission and, on a LayerZero leg, of the fee the OFT keeps. The amounts relate as follows:

```text
totalTokenCommission = percentFee + baseFee
totalTokenFee        = totalTokenCommission + oftFee   (oftFee counts as 0 when omitted)
amount               = receiveAmount + totalTokenFee
```

| Field | Meaning |
| --- | --- |
| `receiveAmount` | Amount that arrives, in token base units |
| `totalTokenCommission` | Bridge commission in the token: `percentFee` plus `baseFee` |
| `totalTokenFee` | Everything kept from `amount` in the token: `totalTokenCommission` plus `oftFee` |
| `percentFee`, `baseFee` | Percentage and flat parts of the bridge commission |
| `minAmount` | The bridge contract's floor for the route: `minFundsInAmount` for a mint, `minFundsOutAmount` for a burn. Read live, so it can change |
| `oftFee` | What the USDT0 OFT keeps on a LayerZero leg, in token base units. Omitted on a direct route |
| `lzNativeFee` | LayerZero messaging fee in the paying chain's native base units. The depositor pays it on a mint, the bridge pays it on a burn. Never deducted from `receiveAmount`. Omitted on a direct route |
| `networkFee` | The depositor's gas for a mint, in the source chain's native base units, including `approveNetworkFee`. Omitted on a burn |
| `approveNetworkFee` | The part of `networkFee` that pays a token approval still needed. Omitted when the allowance already covers the amount |
| `networkFeeInToken`, `lzNativeFeeInToken` | The native fees valued in the token at the market rate. Omitted when not applicable or when the rate is unavailable |
| `transactionCost` | Everything the user pays, in token base units: `totalTokenFee` plus the `InToken` values that are present |
| `estimatedDeliverySeconds`, `estimatedDeliverySecondsP90` | Median and 90th percentile delivery time of the route's recent completed transfers. Omitted while too few have completed |

An `amount` below `minAmount` returns `400` with code `2` and `details: {"amount": "...", "minAmount": "..."}`.

The fee schedule is deployment-specific; the numbers in this section are illustrative. The way the quote is calculated depends on whether Arbitrum or an entrypoint-based network is the mint source.

### Direct mint estimate from Arbitrum

For Arbitrum One, the gross `amount` is deposited directly into the bridge contract. Quote a gross deposit of 1 USDT or USDT0 like this:

```bash
curl -H "X-API-Key: <API_KEY>" https://transfer.gateway.stage.utexo.com/api/v0/mint-burn/estimate/42161/827166/2/1000000
```

No `senderAddress` is required for the direct Arbitrum route. There is no `oftFee` on this route, so:

```text
receiveAmount + totalTokenCommission = amount
```

Use the same gross `amount` in `POST /mint/op-id`. Its `depositAmount` is the value approved and passed to `fundsIn`, while `mintAmount` is the quoted net RGB amount.

### Mint estimate from an entrypoint-based network

Ethereum, Polygon PoS, Plasma, and Tron use a two-stage quote:

1. The source entrypoint quotes how much of the gross deposit is guaranteed to arrive at the Arbitrum bridge.
2. The bridge calculates its token commission on that guaranteed Arbitrum delivery and returns the final RGB `receiveAmount`.

The estimate must include `senderAddress`, because the entrypoint quote and generated deposit parameters depend on the source account. For example, quote a Polygon deposit:

```bash
curl -H "X-API-Key: <API_KEY>" "https://transfer.gateway.stage.utexo.com/api/v0/mint-burn/estimate/137/827166/<SOURCE_TOKEN_ID>/1000000?senderAddress=0xYourPolygonAddress"
```

Use the same pattern for the other entrypoint-based networks:

| Source | Estimate path | `senderAddress` format |
| --- | --- | --- |
| Ethereum | `/mint-burn/estimate/1/827166/{tokenId}/{amount}` | `0x` EVM address |
| Polygon PoS | `/mint-burn/estimate/137/827166/{tokenId}/{amount}` | `0x` EVM address |
| Plasma | `/mint-burn/estimate/9745/827166/{tokenId}/{amount}` | `0x` EVM address |
| Tron | `/mint-burn/estimate/728126428/827166/{tokenId}/{amount}` | Base58Check or Tron hex address |

Append `?senderAddress={sourceAccount}` to each path. Discover the source network's USDT token ID through its `supported-tokens` endpoint; do not assume it is identical in every environment.

For an entrypoint-based network, `oftFee` is the part of the deposit that LayerZero does not deliver to Arbitrum, so:

```text
receiveAmount + totalTokenCommission + oftFee = amount
```

The depositor also pays `lzNativeFee` in the source chain's native currency; it is not deducted from `amount`. The minimum is checked on both the deposit and the amount LayerZero delivers. After `POST /mint/op-id`, use the returned `entrypoint.depositParams`, `nativeFee`, and other entrypoint fields to submit the source-chain deposit; do not construct those values from the estimate.

### Estimate lifecycle and exact receive amounts

The endpoint is read-only: it does not reserve liquidity, prepare a mint, or move funds. Treat the result as a quote, not a reservation. Fees or upstream delivery quotes may change before you prepare or submit the operation; the response from `POST /mint/op-id` is authoritative for that prepared mint.

To target an exact RGB receive amount, search for a gross input whose `receiveAmount` equals the target. Start with the target as the gross input, add the difference between the target and `receiveAmount`, and quote again until the endpoint returns the exact target. Integer rounding and a base fee mean that simply adding one percentage may not produce an exact result.

To recheck the fees of a mint you already prepared and have not paid yet, add `?opId={opId}` (with `senderAddress` if the mint has a stored depositor). The route, token, depositor, and exact gross amount must match the prepared mint, so its reservation is not counted twice against your verification limit. A mint that is closed or expired returns `409` with code `12`: do not pay it.

<Warning>
  Call the estimate before creating the RGB invoice so you can show and record the expected net amount. After `POST /mint/op-id`, verify that `mintAmount` is the amount the customer accepted before moving funds. If the invoice itself carries a fungible amount, it must equal `mintAmount`, not the gross EVM deposit.
</Warning>

## RGB wallet requirements

Utexo's USDT on Bitcoin uses the **BFA (Burnable Fungible Asset)** schema, which allows the asset to be burned for release on a supported EVM network. Use any RGB wallet that supports BFA and can:

- create a **blinded** receive invoice for a mint;
- refresh and settle incoming transfers;
- burn a BFA amount with a 32-byte burn reason (the payout destination);
- report spendable balances and unspent outputs before a burn;
- export the raw consignment of the burn, which you submit to `/unlock`.

The [Utexo SDKs](/product-suite/sdk) provide these operations. Contact the Utexo team to confirm that your wallet stack is compatible with the deployed BFA schema.

Set up the wallet as follows:

- Create the wallet keys once, store them securely, and load the same keys and data directory after every restart. Do not run two processes against the same wallet data at the same time.
- Configure an EVM RPC endpoint. The wallet needs it to validate the bridge history referenced by BFA consignments.
- Fund the wallet with Bitcoin on the configured network. After the funding transaction confirms, create RGB-colorable UTXOs. This broadcasts a Bitcoin transaction.
- Wait until the wallet reports usable allocation capacity before you create an invoice. Each pending blinded invoice reserves an allocation slot. Use a new invoice for every mint, and clean up only invoices that have definitely expired.

## Lock and mint

<Steps>
  <Step title="Quote the gross deposit">
    Call the estimate endpoint with the source EVM network, RGB destination network, EVM token ID, and proposed gross deposit. Record `receiveAmount` as the amount the RGB wallet should receive.

    If the customer specifies the desired RGB amount instead, iterate estimates as described in [Estimate the result](#estimate-the-result) to find an exact gross input.
  </Step>
  <Step title="Create a blinded RGB invoice">
    A bridge mint requires a **blinded** recipient. Do not use a witness invoice: a witness recipient requires a satoshi amount in the Bitcoin output, while the bridge mint does not carry one.

    Create a new blinded receive invoice in the RGB wallet:

    - leave the asset ID out of the invoice, and leave the assignment unspecified (the bridge binds the prepared mint amount);
    - set an expiry, for example 24 hours;
    - use the Utexo RGB proxy as the transport endpoint;
    - require 1 confirmation before the receive settles.

    Persist the invoice and the wallet's transfer reference with your operation state. For a bridge mint, the invoice normally has an unspecified assignment; the bridge binds the prepared `mintAmount` to that blinded recipient.

    An invoice may omit the asset ID and amount. If another client produces an invoice that includes an asset ID or fungible assignment, they must match the supported USDT asset and the prepared `mintAmount`.

    Use a new invoice for every mint. The Mint refuses an invoice it has already paid.
  </Step>
  <Step title="Prepare the mint">
    Send the blinded invoice and the **gross source deposit** from the estimate as `amount`:

    ```bash
    curl -X POST https://transfer.gateway.stage.utexo.com/api/v0/mint/op-id \
      -H "X-API-Key: <API_KEY>" \
      -H "Content-Type: application/json" \
      -d '{
        "networkId": 827166,
        "sourceNetworkId": 42161,
        "tokenId": 2,
        "assetId": "<RGB_ASSET_ID>",
        "invoice": "rgb:...",
        "amount": 1000000
      }'
    ```

    ```json
    {
      "opId": "9f2c...e41a",
      "ttlSeconds": 600,
      "settlementData": "0x9f2c...e41a",
      "depositAmount": "1000000",
      "mintAmount": "989500"
    }
    ```

    Before moving funds, verify all of the following:

    - `depositAmount` equals the gross amount you intend to deposit;
    - `mintAmount` equals the amount in the blinded invoice and the amount the customer accepted;
    - `settlementData` is retained byte-for-byte for the contract call;
    - enough time remains in `ttlSeconds` for the deposit to be submitted.

    The deposit must reach the bridge contract before the operation expires. If it expires, prepare a new operation and use a new invoice.
  </Step>
  <Step title="Lock USDT or USDT0">
    Approve the bridge contract to spend exactly `depositAmount`. If the token requires resetting an existing allowance, set it to `0` first. Then call `fundsIn` with the returned `settlementData` unchanged. `destinationAddress` is an empty string because the RGB recipient was supplied in the invoice.

    ```ts
    import { createWalletClient, http, parseAbi } from "viem";
    import { arbitrum } from "viem/chains";

    const bridgeAbi = parseAbi([
      "function fundsIn(uint256 amount, uint256 destinationChainId, string destinationAddress, bytes settlementData) payable returns (bytes32 operationId)",
    ]);
    const erc20Abi = parseAbi([
      "function approve(address spender, uint256 amount) returns (bool)",
    ]);

    // wallet: a viem wallet client for your EVM account on Arbitrum
    await wallet.writeContract({
      address: sourceToken,
      abi: erc20Abi,
      functionName: "approve",
      args: [bridgeContract, BigInt(depositAmount)],
    });

    await wallet.writeContract({
      address: bridgeContract,
      abi: bridgeAbi,
      functionName: "fundsIn",
      args: [BigInt(depositAmount), 827166n, "", settlementData],
    });
    ```

    Submit the exact prepared amount. A different amount will not match the prepared mint.
  </Step>
  <Step title="Track the mint">
    Poll the mint until it reaches `completed` or `expired`:

    ```bash
    curl https://transfer.gateway.stage.utexo.com/api/v0/lock/9f2c...e41a/status \
      -H "X-API-Key: <API_KEY>"
    ```

    | Status | Meaning |
    | --- | --- |
    | `awaiting_funds_in` | Waiting for the matching deposit, until `expiresAt` |
    | `funds_in_confirmed` | The deposit was found and matches the prepared mint |
    | `bridge_signed` | The mint signer signed the mint |
    | `broadcast` | The Bitcoin transaction anchoring the mint was broadcast |
    | `completed` | The Bitcoin transaction is confirmed; the mint is complete |
    | `expired` | No matching deposit arrived in time |

    Signing starts only after the deposit is final on Arbitrum, so `funds_in_confirmed` can last for a while before `bridge_signed`.
  </Step>
  <Step title="Receive the USDT in the RGB wallet">
    Refresh the wallet until the incoming transfer settles. Then read the USDT balance.

    A pending (future) balance includes transfers known to the wallet. The spendable balance is what is available to burn or transfer now. Do not start a burn until the required amount is spendable.

  </Step>
</Steps>

### Deposit from another network

From Ethereum, Polygon PoS, Plasma, or Tron, quote and prepare the mint with that network as `sourceNetworkId`. Include the depositor in the estimate's `senderAddress` query parameter and in the `/mint/op-id` request's `sourceAddress`, and include the source `tokenId`.

`amount` remains the gross amount deposited on the source network. The response adds an `entrypoint` object; `mintAmount` is the net amount quoted to arrive as USDT on RGB after the upstream delivery and bridge commission.

Instead of calling `fundsIn` directly:

1. Approve `entrypoint.contractAddress` to spend `depositParams.amountLD` of the source token.
2. Call `deposit(depositParams)` on the entrypoint contract with `entrypoint.nativeFee` as the transaction value.

```ts
const entrypointAbi = parseAbi([
  "function deposit((uint256 amountLD, uint256 minAmountLD, bytes extraOptions, bytes payload, address refundTo, uint256 expectedComposeValue) depositParams) payable returns (bytes32 guid)",
]);

await wallet.writeContract({
  address: entrypoint.contractAddress,
  abi: entrypointAbi,
  functionName: "deposit",
  args: [{
    amountLD: BigInt(p.amountLD),
    minAmountLD: BigInt(p.minAmountLD),
    extraOptions: `0x${p.extraOptions}`,
    payload: `0x${p.payload}`,
    refundTo: p.refundTo,
    expectedComposeValue: BigInt(p.expectedComposeValue),
  }],
  value: BigInt(entrypoint.nativeFee),
});
```

`p` is `entrypoint.depositParams`. `extraOptions` and `payload` are returned without the `0x` prefix. On Tron, make the equivalent calls with TronWeb. Then track the mint with `GET /lock/{opId}/status`.

## Burn and unlock

<Warning>
  A burn cannot be undone. Check the quote, minimum amount, release capacity, spendable RGB balance, and payout destination before calling the wallet. The payout destination is committed into the burn and cannot be changed by `/unlock`.

  **The legacy padded EVM address works only for a release on Arbitrum.** A burn whose recipient is 12 zero bytes plus a 20-byte address is paid by a direct `fundsOut` on Arbitrum and nothing else. To release on Ethereum, Polygon PoS, Plasma, or Tron, the burn must commit a V1 burn destination hash, and `/unlock` must carry the matching `burnDestination` record. A legacy burn sent to a LayerZero destination is refused with `400`. See [Choose the burn destination](#choose-the-burn-destination).
</Warning>

### Choose the burn destination

A BFA burn has one 32-byte field for the payout target, the burn reason (`burnReason`). It holds one of two formats:

| Version | The 32 bytes hold | Release routes |
| --- | --- | --- |
| V0 (legacy) | 12 zero bytes followed by the 20-byte EVM address | Direct `fundsOut` on Arbitrum only. `/unlock` must not carry `burnDestination` |
| V1 | `hash_v1(record)` of a burn destination record | Direct `fundsOut` on Arbitrum, or `lzFundsOut` through USDT0 / LayerZero. `/unlock` must carry the record |

The bridge tells them apart by the high 12 bytes: all zero means V0, otherwise V1.

A V1 record has four fields:

| Field | Type | Rule |
| --- | --- | --- |
| `version` | uint32 | Always `1` |
| `destinationChainId` | uint64 | Network ID of the payout network. Must equal `destinationNetworkId` of `/unlock`. Not `0` |
| `dstEid` | uint32 | LayerZero endpoint ID of the payout network. `0` means a direct `fundsOut` on Arbitrum |
| `recipient` | bytes | Chain-native payee, 1 to 32 bytes, `0x` hex. Exactly 20 bytes when `dstEid` is `0` |

The hash is the EIP-712 `hashStruct` of the record:

```text
TYPEHASH_V1 = keccak256("UtexoBurnDestinationV1(uint64 destinationChainId,uint32 dstEid,bytes recipient)")
            = 0xa1cba9d766975eb04c6a31c3b68dbb2381444a222c9972b6bf3ab26fcb829b00

hash_v1 = keccak256(abi.encode(TYPEHASH_V1, uint64 destinationChainId, uint32 dstEid, keccak256(recipient)))
```

The routes the Utexo web app uses:

| Payout network | `destinationChainId` | `dstEid` | `recipient` |
| --- | ---: | ---: | --- |
| Arbitrum One | `42161` | `0` | 20-byte EVM address |
| Ethereum | `1` | `30101` | 20-byte EVM address |
| Polygon PoS | `137` | `30109` | 20-byte EVM address |
| Plasma | `9745` | `30383` | 20-byte EVM address |
| Tron | `728126428` | `30420` | 21-byte Tron address: the Base58Check address decoded, without its 4-byte checksum (starts with `0x41`) |

Confirm the route list for your environment with the Utexo team before you burn.

Compute the hash, for example with viem:

```ts
import { encodeAbiParameters, keccak256, toBytes } from "viem";

const TYPEHASH_V1 = keccak256(
  toBytes("UtexoBurnDestinationV1(uint64 destinationChainId,uint32 dstEid,bytes recipient)"),
);

// Example: release to Polygon PoS
const burnDestination = {
  version: 1,
  destinationChainId: 137,
  dstEid: 30109,
  recipient: "0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266",
} as const;

const burnReason = keccak256(
  encodeAbiParameters(
    [{ type: "bytes32" }, { type: "uint64" }, { type: "uint32" }, { type: "bytes32" }],
    [
      TYPEHASH_V1,
      BigInt(burnDestination.destinationChainId),
      burnDestination.dstEid,
      keccak256(burnDestination.recipient),
    ],
  ),
);
// burnReason is the 32-byte value committed in the burn.
```

Test your implementation against the published vectors before you burn. For example, `destinationChainId` `1`, `dstEid` `30101` and recipient `0x2222222222222222222222222222222222222222` give `0x9274beba7130d3f8a4ef95c5c4c555616718050c688f8478e23f8131762a9537`.

<Warning>
  Store the `burnDestination` record with the burn. A V1 burn cannot be released without the exact record whose hash it commits.
</Warning>

<Steps>
  <Step title="Quote the burn">
    Quote the gross amount to burn by reversing the route:

    ```bash
    curl -H "X-API-Key: <API_KEY>" https://transfer.gateway.stage.utexo.com/api/v0/mint-burn/estimate/827166/42161/2/1000000
    ```

    Show the customer both the gross burn and `receiveAmount`. The recipient receives `receiveAmount`; `totalTokenFee` (the bridge commission plus, on a LayerZero release, `oftFee`) is deducted. Do not burn less than `minAmount`. The quote does not check current release liquidity, so perform the capacity check separately.
  </Step>
  <Step title="Check release capacity">
    ```bash
    curl -H "X-API-Key: <API_KEY>" https://transfer.gateway.stage.utexo.com/api/v0/unlock/capacity/827166/42161/<EVM_TOKEN_ID>
    ```

    ```json
    {
      "srcNetworkId": 827166,
      "networkId": 42161,
      "tokenId": 2,
      "poolBalance": "1354199",
      "pendingReleases": "0",
      "availableOutflow": "135419",
      "available": "135419"
    }
    ```

    Do not burn more than `available`. It is the available USDT or USDT0 liquidity in the bridge, less releases in progress, capped by the current outflow limit when one is set. Also do not burn less than the estimate's `minAmount` (the Arbitrum bridge's `minFundsOutAmount`). Capacity is a snapshot and is not reserved for you, so recheck it immediately before the burn.
  </Step>
  <Step title="Prepare the RGB wallet">
    Refresh the wallet and check two things:

    - the spendable BFA balance covers the burn amount;
    - there is an empty colorable UTXO (no RGB allocations, no pending blinded receive) with sats for the Bitcoin transaction, for example at least 1000 sats.

    If no suitable UTXO is available, fund the wallet if necessary and create colorable UTXOs before you continue.
  </Step>
  <Step title="Burn in the RGB wallet">
    Build the 32-byte burn reason:

    - **Release on any network other than Arbitrum:** use the V1 `burnReason` from [Choose the burn destination](#choose-the-burn-destination), and keep its record.
    - **Release on Arbitrum only:** you can use the legacy V0 value. Remove `0x` from the 20-byte EVM address, lowercase it, check that it has 40 hexadecimal characters, and left-pad it with 24 zeroes:

    ```text
    EVM address:    f39fd6e51aad88f6f4ce6ab8827279cfffb92266
    Burn recipient: 000000000000000000000000f39fd6e51aad88f6f4ce6ab8827279cfffb92266
    ```

    Then burn the gross RGB amount in the wallet, with the burn reason, a Bitcoin fee rate, and your confirmation policy. The wallet builds and signs the PSBT, writes the BFA consignment, and broadcasts the Bitcoin anchor transaction.

    Persist the burn transaction ID and the wallet's transfer reference before you continue. If the call fails after submission and it is unclear whether a transaction was created, check the wallet's transfer list before you retry. Never retry an ambiguous burn automatically.

  </Step>
  <Step title="Read and encode the burn consignment">
    Export the consignment that the burn created from the RGB wallet. Base64-encode the raw bytes.

    Send the result as the `consignment` field of `/unlock`. Do not encode the path or a hex representation of the file; `/unlock` expects standard base64 of the raw consignment bytes.

    Optionally, send the same body to `POST /unlock/verify` first. It runs the checks `/unlock` runs before it claims the burn (burn shape, bridged asset, payout destination, outflow capacity) and returns `operationId`, `amount`, `recipient`, `assetId`, and `burnTxid`. Nothing is claimed or sent, so it can be repeated. It does not check Bitcoin finality, the deposits behind earlier mints, or the reject list.

  </Step>
  <Step title="Submit the burn">
    ```bash
    curl -X POST https://transfer.gateway.stage.utexo.com/api/v0/unlock \
      -H "X-API-Key: <API_KEY>" \
      -H "Content-Type: application/json" \
      -d '{
        "consignment": "<BASE64_CONSIGNMENT>",
        "srcNetworkId": 827166,
        "destinationNetworkId": 42161,
        "tokenId": 2,
        "maxFeeRate": "1000000000"
      }'
    ```

    `maxFeeRate` is optional. When supplied, it is a non-negative decimal string containing the maximum EVM gas price in wei that you accept.

    For a V1 burn, add the record the burn commits to. Do not send `burnDestination` for a legacy V0 burn:

    ```json
    "burnDestination": {
      "version": 1,
      "destinationChainId": 42161,
      "dstEid": 0,
      "recipient": "0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266"
    }
    ```

    Submit right after the burn; you do not need to wait for Bitcoin confirmations. The signer enclaves require 6 confirmations of the burn before they sign, and the bridge waits for them itself. The amount and payout destination are read from the consignment and cannot be overridden by the request.
  </Step>
  <Step title="Confirm the release">
    A successful submission returns `200` with one of two statuses:

    ```json
    {
      "evmTxHash": "0xabc...",
      "status": "submitted",
      "recipient": "0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266",
      "operationId": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
    }
    ```

    | Status | Meaning |
    | --- | --- |
    | `submitted` | The release transaction was sent. It is not yet a confirmation: follow `evmTxHash` until it confirms |
    | `confirming` | The burn is accepted and claimed, but not final on Bitcoin yet. Nothing was sent and `evmTxHash` is empty. The bridge sends the release itself once the burn is final. Do not resend: a second `/unlock` of the same burn returns `409` |

    `operationId` is the keccak256 of the consignment. The transfer history lists the burn under it: `SOURCE_IN` while it waits for Bitcoin finality, `SIGNING` while the release is signed, `DEST_OUT` once it is out, and `SETTLED` once it is paid. A burn whose release does not go out within 24 hours (for example, because its Bitcoin transaction was replaced or dropped) shows as `FAILED` and can be unlocked again.

    Verify that `recipient` is the payee committed in the burn. The recipient receives the estimate's `receiveAmount`.
  </Step>
</Steps>

### Release to another network

To release to Ethereum, Polygon PoS, Plasma, or Tron, use that network as the destination in every burn request, and use the token ID of USDT on that network:

```bash
curl -H "X-API-Key: <API_KEY>" https://transfer.gateway.stage.utexo.com/api/v0/mint-burn/estimate/827166/137/<DESTINATION_TOKEN_ID>/1000000
curl -H "X-API-Key: <API_KEY>" https://transfer.gateway.stage.utexo.com/api/v0/unlock/capacity/827166/137/<DESTINATION_TOKEN_ID>
```

The burn must commit a V1 burn destination for that network (see [Choose the burn destination](#choose-the-burn-destination)); a legacy padded address is refused. In `POST /unlock`, set `destinationNetworkId` to the destination network, send the `burnDestination` record, and set `tokenId`, which is required for these releases:

```json
{
  "consignment": "<BASE64_CONSIGNMENT>",
  "srcNetworkId": 827166,
  "destinationNetworkId": 137,
  "tokenId": <DESTINATION_TOKEN_ID>,
  "burnDestination": {
    "version": 1,
    "destinationChainId": 137,
    "dstEid": 30109,
    "recipient": "0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266"
  }
}
```

The bridge releases from Arbitrum with `lzFundsOut` and sends the funds through USDT0 / LayerZero, so `evmTxHash` is the Arbitrum transaction. A confirmed Arbitrum transaction means the send was submitted; delivery to the recipient happens later, in a separate transaction on the destination network. The estimate's `oftFee` covers what the OFT keeps on delivery, and `receiveAmount` is what arrives. The bridge pays the LayerZero messaging fee (`lzNativeFee`).

## Retries and errors

Errors have the shape `{"error":"...","code":4,"details":{...}}`. `details` is present only when the error has structured retry information.

| HTTP | Code | When | What to do |
| --- | --- | --- | --- |
| `400` | `65535` | Route, network, token, address, or amount is invalid; the amount does not cover commission; or on `/unlock`, the consignment is not a burn, has no burn reason, or its `burnDestination` is missing, wrong, or sent for a legacy burn | Correct the request; do not continue with a burn |
| `400` | `2` | The amount is below the route's minimum (`details.amount`, `details.minAmount`) | Raise the amount |
| `400` | `4` | `/unlock`: the release is above the current outflow limit | Wait and retry. The burn remains redeemable |
| `401` | - | The API key or session is missing or invalid | Check the key |
| `403` | `9` | Estimate or `/mint/op-id`: the mint would exceed the verification limit of an account without KYC or KYB | Complete verification |
| `404` | - | `/lock/{opId}/status`: unknown `opId`. `/unlock`: unknown network, or the burn cites a mint this bridge never prepared | Check the identifiers |
| `409` | - | `/mint/op-id`: the invoice is already used or belongs to another preparation, or the unpaid-mint limit is reached. `/unlock`: the burn was already released or is being released, `confirming` included | Use a new invoice; for a burn, do not submit another release, follow the transfer history |
| `409` | `12` | Estimate with `opId`: the prepared mint is closed or expired | Do not pay it; check its status |
| `409` | `6`, `7`, `8` | `/unlock`: the bridge could not keep the burn waiting for Bitcoin finality (relay behind the burn block, too few confirmations, or relay depth refused) | Retry the same request later |
| `422` | `10` | `/unlock`: the asset's reject list rejects a coin the burn descends from | Do not retry; the signers refuse it on every attempt |
| `429` | - | Rate limit | Back off with jitter and retry |
| `500` | - | Validation, signing, or submission failed | Reconcile operation state before retrying, then contact Utexo with the `opId` or burn `operationId` |
| `503` | - | The route's commission cannot be priced, a LayerZero quote is unavailable, or another mint on the wallet is not broadcast yet | Do not prepare or submit; retry later |
| `503` | `11` | `/mint/op-id`: the mint wallet has no bridge right to spare | Retry the same request later; it refills itself |

On `POST /mint/op-id`, a `400` may indicate that the deposit does not cover the commission, the invoice is malformed, the invoice uses a witness recipient, the invoice amount or asset does not match, or the route is invalid. A `409` indicating that the RGB invoice was already used means you must create a new blinded invoice. Sending the same request again for a prepared mint that is not paid yet resumes it; the retry never renews the original deadline.

For unlock codes `6`, `7`, and `8`, and for a `confirming` response, nothing was sent to the destination EVM network, and retrying the same request with the same consignment is safe. For transport errors or a `500` during an irreversible or externally submitted step, first reconcile the RGB wallet, bridge status, and EVM transaction state. Do not assume the operation failed merely because the response was lost.
