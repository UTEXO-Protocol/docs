Use **[`@utexo/wdk-wallet-rgb`](/sdk/wdk-wallet-rgb)** for Node.js on-chain RGB integrations. This guide prepares a BFA transfer on public Bitcoin signet.

<Info>
  For mobile, see the [React Native guide](/getting-started/quickstart/react-native). For browsers, see the [Web guide](/getting-started/quickstart/web). Lightning remains WIP, testing-only, and not recommended for production.
</Info>

## Prerequisites

- Node.js `^22.21.0` or `>=24.9.0`, using ES modules
- A matching `utexo-rgb-native` worker and its verified SHA-256
- Signet BTC for fees on both sender and receiver wallets
- A separately initialized sender account holding a compatible BFA asset
- The expected asset ID from verified deployment metadata
- Secure mnemonic storage, a private persistent directory per wallet, and application-owned transaction approval

The staging RGB profile requires a compatible BFA issuance and matching bridge services. Verify the asset's compatibility before proceeding with transfer steps. See [BFA compatibility](/sdk/wdk-wallet-rgb#assets-and-bfa).

Never use mainnet keys or real funds in this signet guide.

## Step 1: Install the SDK

```bash
npm install @utexo/wdk-wallet-rgb@latest
```

Package installation alone does not provide the matching native executable. See [installation](/sdk/wdk-wallet-rgb#installation) for native worker setup.

## Step 2: Open and Connect the Wallet

Load a saved BIP39 mnemonic from secure application storage. For a new wallet, generate and save a separate mnemonic first.

```javascript
import WalletManagerRgb from '@utexo/wdk-wallet-rgb';
import { resolve } from 'node:path';

const nativeExecutable = process.env.UTEXO_RGB_NATIVE_EXECUTABLE;
const nativeSha256 = process.env.UTEXO_RGB_NATIVE_SHA256;
if (!nativeExecutable || !nativeSha256) {
  throw new Error('Configure the verified native worker path and SHA-256');
}

const mnemonic = await loadMnemonicFromSecureStorage();
const manager = new WalletManagerRgb(mnemonic, {
  network: 'signet',
  mode: 'rgb',
  profile: 'staging',
  startupMode: 'offline',
  dataDir: resolve('./wallet-data/signet-receiver'),
  indexerUrl: 'ssl://stage.electrs-signet.mint.utexo.com:60602',
  transportEndpoint: 'rpcs://staging.rgb-proxy.utexo.com/json-rpc',
  evmRpcUrls: { '42161': 'https://arb1.arbitrum.io/rpc' },
  nativeExecutable,
  nativeSha256,
  maxFeeSats: 5000n,
  authorize: (review) => requestWalletApproval(review),
});

const wallet = await manager.getAccount();
await wallet.connect();
```

`loadMnemonicFromSecureStorage()` and `requestWalletApproval(review)` are application-owned functions. The approval callback returns `true` only after the application approves the exact recipient, amount, fee, and transaction plan. `nativeExecutable` must be an absolute path to the matching worker; the hash must come from the verified build.

The network is **public Bitcoin signet**. The SDK accepts only the pinned Electrum indexer above; `https://mempool.space/signet/api` is an Esplora endpoint and cannot be used as its `indexerUrl`. The staging proxy is `https://staging.rgb-proxy.utexo.com/json-rpc`, represented by the required `rpcs://` URI in the SDK.

Give the sender a separate mnemonic, manager, and storage directory, using the same signet staging profile. Opening in offline mode permits cached reads; `connect()` is required before allocating addresses, creating invoices, or spending.

## Step 3: Fund the Wallet

```javascript
const address = await wallet.getAddress();
console.log('Deposit address:', address);
console.log('Spendable BTC (sats):', await wallet.getBalance());
```

Send signet BTC and wait for confirmations. The sender also needs BTC for fees and a spendable RGB balance.

## Step 4: Prepare RGB Outputs

```javascript
const outputOperationId = await createAndSaveOperationId('receiver-rgb-outputs');
const outputs = await wallet.createUtxos({
  operationId: outputOperationId,
  count: 5,
  size: '2000',
  feeRate: '2',
});
console.log('RGB output transaction:', outputs.txid);
```

`createAndSaveOperationId()` is an application-owned function that persists a unique ID before submitting a new operation. After interruption, recover the saved operation rather than generating another ID and resubmitting. The authorization callback runs before signing.

`size` is in satoshis and `feeRate` is in sat/vB. Both use strings or `bigint`; `count` is a number. Wait for the output transaction's required confirmations before receiving.

## Step 5: Resolve the BFA Asset

`senderWallet` is the separately connected and funded account. Set `expectedAssetId` from the verified staging deployment metadata.

```javascript
const assets = await senderWallet.listAssets();
const asset = assets.find(
  (item) => item.assetId === expectedAssetId && item.schema === 'Bfa',
);
if (!asset) throw new Error('The sender does not hold the expected BFA asset');

const assetId = asset.assetId;
const amount = 10n ** BigInt(asset.precision); // one displayed unit
```

This API returns a flat asset array, not a `bfa` collection. Do not use a ticker alone to select the asset. Amounts use integer base units as decimal strings or `bigint`.

## Step 6: Create a Receive Invoice

```javascript
const receiveData = await wallet.blindReceive({
  amount,
  expirationSeconds: 3600,
  minConfirmations: 3,
});
console.log('RGB invoice:', receiveData.invoice);
```

Omit `assetId` when the receiver has not registered or received the asset yet. The sender specifies it explicitly. `createRgbInvoice({ mode: 'blind', ... })` provides the same receive flow.

## Step 7: Send From the Funded Account

```javascript
const sendOperationId = await createAndSaveOperationId('send-bfa');
const result = await senderWallet.sendRgbInvoice({
  operationId: sendOperationId,
  invoice: receiveData.invoice,
  assetId,
  amount,
  feeRate: '2',
  minConfirmations: 3,
});
console.log('Transfer transaction:', result.txid);
```

The sender validates the invoice's network, asset, amount, recipient key, and proxy before preparing the transaction. Witness invoices additionally require `witnessAmountSats`. Use `sendRgbInvoice()` for RGB transfers.

## Step 8: Refresh and Verify

```javascript
await senderWallet.refreshTransfers({ assetId });
await wallet.refreshTransfers({ assetId });

console.log('Receiver transfers:', await wallet.listTransfers({ assetId }));
console.log('Receiver balance:', await wallet.getAssetBalance(assetId));
```

Repeat refreshes while consignments arrive and Bitcoin confirmations accumulate. Inspect transfer status until settlement; one refresh is not a settlement guarantee.

## Step 9: Recover Interrupted Operations and Close

If the application loses a send response after submission was attempted, reopen the same wallet directory and recover using the saved ID:

```javascript
const recovered = await senderWallet.recoverSend(sendOperationId);
console.log('Recovered send state:', recovered.state);
```

Use `getOperation()` and `listUnresolvedOperations()` to inspect state. Output creation uses `recoverCreateUtxos()` after submission was attempted; an interrupted `starting` or `prepared` operation uses `recoverUnsubmittedOperation()`. An unresolved result requires reconciliation, not another payment under a new ID.

```javascript
await manager.shutdown();
```

Await shutdown on the sender's manager as well. Preserve complete wallet state and operation journals through the application's backup process. The SDK has no `createBackup()` or `restoreAccountFromBackup()` API, and a mnemonic alone does not recover RGB state.

## Troubleshooting

| Issue | Check |
| --- | --- |
| Constructor rejects the network or endpoint | Use `signet`, `mode: 'rgb'`, `profile: 'staging'`, and the exact Electrum, proxy, and EVM RPC settings above |
| `NATIVE_IDENTITY_MISMATCH` | Use the worker and hash matching the SDK build |
| `WALLET_OFFLINE` | Call `connect()` before address allocation, invoices, or transaction preparation |
| `AUTHORIZATION_DECLINED` | The application did not approve the transaction review |
| BFA asset is missing or incompatible | Check the official asset ID, schema, contract export, and matching staging deployment |
| Operation already exists or remains unresolved | Inspect and recover the original persisted operation ID |
| Transfer stays pending | Refresh both wallets and inspect transfer results and Bitcoin confirmations |
