<Info>
  This guide covers Node.js server applications. For mobile, see the [React Native guide](/getting-started/quickstart/react-native). For browser applications, see the [Web guide](/getting-started/quickstart/web).
</Info>

This guide uses [`@utexo/wdk-rgb-lightning`](/sdk/wdk-rgb-lightning), the current Node.js / Bare module for RGB and RGB-over-Lightning. It runs an `rgb-lightning-node` (LDK + `rgb-lib`) node in-process behind WDK's wallet-manager/account contract. The mnemonic stays in the WDK secret manager; channel-state cryptography runs in-process through a VLS signer.

<Warning>
  `@utexo/wdk-rgb-lightning` is a pre-1.0 beta. This guide was checked against `0.2.0-beta.5` with `@utexo/rgb-lightning-node-nodejs` `0.2.0-beta.5` (RLN `v0.17.0-beta.3`). `0.2.0-beta.5` requires the native binding at exactly the same version. APIs may change between releases — check the installed package's `index.d.ts` before upgrading.
</Warning>

<Note>
  The archived `@utexo/rgb-sdk` package (`UTEXOWallet`, `initialize()`, `send()`) is no longer used for new Node.js integrations. Do not mix its method names into WDK code.
</Note>

## Prerequisites

- Node.js 18 or later, on a platform supported by the prebuilt `@utexo/rgb-lightning-node-nodejs` binding
- An ES module project (`"type": "module"` in `package.json`), since the package ships as pure ESM
- Signet BTC for transaction fees, from a public signet faucet
- A separately initialized sender wallet that already holds the RGB asset for an end-to-end transfer
- Secure server-side storage for the mnemonic and a persistent, access-controlled data directory

<Warning>
  This guide uses the public Bitcoin `signet`, the network of the Mint staging environment. Never use mainnet keys or real funds while following this guide.
</Warning>

## Step 1: Install the SDK

```bash
npm install @utexo/wdk-rgb-lightning@0.2.0-beta.5 @utexo/rgb-lightning-node-nodejs@0.2.0-beta.5
```

`@utexo/rgb-lightning-node-nodejs` is the native binding for Node.js. It is an optional peer dependency, so install it explicitly. Its `postinstall` downloads a prebuilt native artifact; no Rust toolchain is required.

On Node.js, `import '@utexo/wdk-rgb-lightning'` resolves to the Node entry point and wires this binding automatically. For Bare / React Native worklets, install `@utexo/rgb-lightning-node-bare` instead.

## Step 2: Generate a Seed Phrase

`WalletManagerRgbLightning` extends WDK's `WalletManager`, so the standard seed helpers are available:

```javascript
import WalletManagerRgbLightning from '@utexo/wdk-rgb-lightning';

const mnemonic = WalletManagerRgbLightning.getRandomSeedPhrase();

if (!WalletManagerRgbLightning.isValidSeedPhrase(mnemonic)) {
  throw new Error('Invalid seed phrase');
}
```

Store the mnemonic securely. Do not log it in production or commit it to source control. Re-using the same mnemonic and `dataDir` reproduces the same Lightning node identity across restarts.

## Step 3: Create the Wallet and Unlock the Node

Construct the manager with the seed and config, get the single account, then bring the node online with `unlock()`:

```javascript
const manager = new WalletManagerRgbLightning(mnemonic, {
  network: 'signet',
  dataDir: './wallet-data/receiver',
});

const wallet = await manager.getAccount(0); // RGB Lightning is single-account

const indexerUrl = 'https://mempool.space/signet/api'; // public signet Esplora

await wallet.unlock({
  ldk_chain_sync: {
    mode: 'TransactionSync',
    config: { indexer_url: indexerUrl },
  },
  indexer_url: indexerUrl,
  proxy_endpoint: 'rpcs://proxy.iriswallet.com/0.2/json-rpc', // public signet RGB proxy
  announce_addresses: [],
  announce_alias: 'my-node',
});
```

`network` and `dataDir` are required at construction. `unlock()` takes the node's chain backend in `ldk_chain_sync` (`TransactionSync` with an Esplora or Electrum indexer, or `BlockSync` with bitcoind RPC), the RGB `indexer_url`, and the RGB transport `proxy_endpoint`. Sender and receiver must use the same network and an RGB proxy that both can reach. Failures throw a typed `UnlockError`.

<Note>
  To receive USDT on Bitcoin (BFA asset schema) minted by the Utexo Mint, also pass `eth_rpc_url`: an Ethereum JSON-RPC endpoint for the chain with the bridge contract (Arbitrum One for the Mint). The node uses it to validate the bridge events behind the asset. Without it the node keeps its non-BFA behavior.
</Note>

<Warning>
  Give every wallet its own `dataDir`. `rgb-lib` takes an exclusive lock on a wallet directory, and the sender and receiver in this guide are separate nodes. A mnemonic is necessary for key recovery, but it does not replace a backup of the RGB and channel state in `dataDir` — see VSS backup in the [reference](/sdk/wdk-rgb-lightning#vss).
</Warning>

## Step 4: Fund the Wallet

```javascript
const address = await wallet.getAddress();
console.log('Deposit address:', address);

const balance = await wallet.getBalance(); // bigint, satoshis
console.log('Spendable BTC (sats):', balance);
```

`getAddress()` throws `AccountLockedError` before `unlock()`. It returns a stable address; call `rotateAddress()` when you need a new one.

Send signet BTC to this address and wait for confirmation before creating RGB UTXOs. Signet blocks arrive about every 10 minutes.

## Step 5: Create RGB UTXOs

RGB allocations live on dedicated ("colored") UTXOs. `createUtxos()` takes RLN's native request:

```javascript
await wallet.createUtxos({
  up_to: false,
  num: 5,
  size: 1000,     // satoshis per UTXO
  fee_rate: 2,    // sat/vB
  skip_sync: false,
});
```

## Step 6: Resolve the Asset From the Sender

`listAssets()` forwards RLN's response, grouped by schema, with the snake_case `asset_id` field. USDT on Bitcoin from the Utexo Mint uses the **BFA** schema, so it is in the `bfa` array. Other test assets are in `nia`, `cfa`, `ifa`, or `uda`.

```javascript
const { bfa } = await senderWallet.listAssets(['Bfa']);
const usdt = (bfa ?? []).find((asset) => asset.ticker === 'USDT');

if (!usdt) {
  throw new Error('The sender wallet does not hold USDT on Bitcoin');
}

const usdtAssetId = usdt.asset_id;
const amount = 10 ** usdt.precision; // one displayed unit in base units
```

A new receiver wallet will not list an asset it has never received. Resolve the ID and precision from the funded sender or an authoritative asset registry. For issuing assets, use [`@utexo/wdk-wallet-rgb`](/sdk/wdk-wallet-rgb).

## Step 7: Create a Receive Invoice

Run this on the receiver wallet created above. `min_confirmations` and `witness` are required; `witness: false` creates a blinded invoice.

```javascript
const receiveData = await wallet.createRgbInvoice({
  min_confirmations: 1,
  witness: false,
  asset_id: usdtAssetId,
  assignment_amount: amount,
  duration_seconds: 3600,
});

console.log('RGB invoice:', receiveData.invoice);
```

`assignment_amount` is an integer in asset base units. One displayed unit equals `10 ** precision` base units; it is not always equal to `1`.

## Step 8: Send From the Funded Wallet

The WDK-standard `transfer()` method recognizes an RGB invoice, decodes it, and builds the native send request for a fungible amount:

```javascript
const sendResult = await senderWallet.transfer({
  recipient: receiveData.invoice,
  amount,
  token: usdtAssetId,
});

console.log('Transfer transaction:', sendResult.hash);
```

For RGB invoices, `hash` is the anchoring Bitcoin txid. `transfer()` also routes BOLT11 invoices, Lightning node pubkeys, and BTC addresses. For non-fungible, multi-recipient, or witness sends, call `sendRgbAsset()` with a full `recipient_groups` request built from `decodeRgbInvoice()` — see the [reference](/sdk/wdk-rgb-lightning#rgb-assets).

The sender must be a separately created and unlocked `WalletAccountRgbLightning` with its own `dataDir`, sufficient signet BTC, and a spendable asset balance.

## Step 9: Refresh and Verify

```javascript
await senderWallet.refreshTransfers({ skip_sync: false });
await wallet.refreshTransfers({ skip_sync: false });

const receivedBalance = await wallet.getTokenBalance(usdtAssetId); // bigint
console.log('Receiver asset balance:', receivedBalance);
```

A transfer can remain pending while its consignment is delivered and its Bitcoin anchor reaches the required confirmation count. Use `listTransfers(assetId)` to inspect its status.

## Step 10: Shut Down

```javascript
manager.dispose();
```

`manager.dispose()` shuts down the native node and wipes retained seed material. Call it on every manager before the process exits.

## Lightning Payments

The same account exposes channels and BOLT11 payments on signet, testnet and regtest. On `mainnet`, Lightning methods throw `LightningDisabledError` (`code: 'LIGHTNING_DISABLED_ON_MAINNET'`) before any network call; on-chain RGB methods keep working. A payment needs a connected peer and an open channel with enough liquidity — unlocking the node does not create either.

```javascript
await wallet.connectPeer(`${peerPubkey}@${peerHost}:${peerPort}`);

await wallet.openChannel({
  peer_pubkey_and_opt_addr: `${peerPubkey}@${peerHost}:${peerPort}`,
  capacity_sat: 500_000,
  push_msat: 0,
  public: false,
  with_anchors: true,
});

const { invoice } = await wallet.createLightningInvoice({
  amountMsat: 3_000_000,
  expirySec: 3600,
});

// On the paying node:
await payerWallet.sendPayment({ invoice });
```

For RGB-over-Lightning, pass `asset_id` / `asset_amount` when opening the channel and creating the invoice. RGB-routed HTLCs have a minimum of 3,000,000 msat. To receive through the Utexo LSP instead of managing channels yourself, configure `lspBaseUrl` and use `account.createLsp()` — see the [wdk-rgb-lightning reference](/sdk/wdk-rgb-lightning).

## Troubleshooting

| Issue | Likely cause | Check |
| --- | --- | --- |
| `Cannot find package '@utexo/rgb-lightning-node-nodejs'` | Native binding not installed | Install the binding next to `@utexo/wdk-rgb-lightning` |
| Native binding version rejected | Binding and WDK versions differ | Install both packages at the same version |
| `UnlockError` | Unreachable indexer or proxy, or an invalid unlock request | Confirm the endpoints match `network` and that `ldk_chain_sync` sets one chain backend |
| `AccountLockedError` | Method called before `unlock()` | Await `unlock()` before address, balance, or send calls |
| Wallet directory lock error | Two wallets share a `dataDir` | Give each wallet its own directory |
| `createUtxos()` fails | Insufficient confirmed BTC | Fund the wallet and wait for confirmation |
| Asset cannot be found | Wrong schema, response shape, or unfunded sender | Read `listAssets().bfa` for USDT on Bitcoin (other schemas for test assets) and use `asset_id` |
| `transfer()` fails | Invoice, amount, balance, or transport problem | Confirm the invoice is unexpired and the amount is in base units |
| Balance does not update | Transfer is pending or wallet is stale | Call `refreshTransfers()` on both wallets and check `listTransfers()` |
